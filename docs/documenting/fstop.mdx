# Fstop 

Learn about how I documented a REST API and its Python SDK.

## Building the docs site

I chose Astro for Fstop's documentation because I was already familiar with it from my current website and a previous API project. 

## The OAS sync pipeline

I knew that I wanted to have API reference docs for the Fstop API, so I had to think about how I would get the OAS file from the codebase to the docs repo. 

To solve this problem, I wrote a Bash script that uses `drf-spectacular` to generate the OAS file from the code and then copy the OAS file to the Fstop API docs repo. 

I created another Bash script in the API docs repo that uses Redocly to build an HTML page from the spec. This means the API reference docs always have the latest endpoints, schemas, and responses. 

In summary, two Bash scripts save me a lot of time and ensure that the API docs are always up to date. 

## The SDK source of truth problem (and how I fixed it)

Originally, I had Speakeasy configuration files in both the Fstop API and the docs repo. It created a huge mess. Things fell out of sync, SDK examples had wrong package names...a big mess. 

So I decided to start fresh: I removed the Speakeasy configuration files from the API code repo and moved it to the SDK repo. Then I changed the config file to pull the OAS file from the API code repo:

```yaml
workflowVersion: 1.0.0
speakeasyVersion: latest
sources:
    Fstop:
        inputs:
            - location: ../fstop/schema.yml # Grab the OAS from here
```

Now there's one source of truth: the OAS file in the Fstop API repo, which is always the latest verison.

## Why no separate SDK docs

The Python SDK is auto-generated from the OpenAPI spec using Speakeasy. Rather than building separate SDK reference documentation, I included Python SDK examples alongside cURL examples in the API feature guides. This serves both audiences: HTTP users see cURL and SDK users see how to accomplish the same task using Python.

Parameter descriptions for functions, return types, and other important information are all captured in docstrings. This means that developers using the SDK in their IDE get inline help without needing to view the docs. 

:::note

The docstrings in the SDK came from the OpenAPI spec. When you define operation summaries, descriptions, and field documentation in your API code, drf-spectacular includes that in the OAS. Speakeasy then reads the OAS and uses it to generate documented functions.

:::

## What worked

Deploying my Astro site with Netlify was a smooth process. The OAS automation pipeline helped to reduce doc drift. 

## Friction points

The main challenge was managing Speakeasy configuration across multiple repos. Splitting the config and pointing it to a single OAS source solved the problem, but it required rethinking the SDK generation workflow.
