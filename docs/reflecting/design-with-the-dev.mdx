# Design with the developer in mind

While building the Fstop API, I had to think about how developers would actually use it. What information do they need? What decisions make an API easier to understand? Where might developers run into friction?

For example, I had to think carefully about how much data each endpoint should return. Returning deeply nested resources could provide more context in a single request, but it could also create larger, more complicated responses. I had to balance providing enough information with keeping responses clear and easy to work with.

Building the API changed how I think about documentation. Documentation is important, but it is only one part of the developer experience. The design of the product itself plays a major role in how easy it is for developers to understand and use.
